# 麦麦省心凑单

保留用户想吃的食品，回答“买哪些套餐、补哪些单品、用哪些已有券、最终多少钱”。这是比价 Skill；不包含下单和付款。读取 [数据规范](references/data-contract.md) 后使用脚本，接入过程见 [真实查询流程](references/live-workflow.md)。

## 确定需求与场景

- 识别每种食品、份数、规格及特制选项。同名不同规格不可互换；套餐替换必须由官方详情支持。必要时集中问一次未明确的规格。
- 确认到店自取或外送、门店/位置、立即用餐或预约。用户要比较两种方式时分别查询、分别计算；不要把自取的券或价格套到外送。
- 默认刚好买齐，`max_extra_units=0`。用户允许多买时设置明确上限，单列多出的食品；不要默默增加或替换。演示例中已明确允许额外一件。
- 外送只读取用户确认使用的地址；不要为了比价创建地址。查询地址列表的个人信息只留在本地。

## 查询与计算

1. 有原生 MCP 工具时优先使用；否则可用 `scripts/mcp_readonly.py`。先读取实时 `tools/list` 的 `inputSchema`，不能把仓库工具简介当作参数定义。
2. 查询对应场景门店、完整分页菜单、相关套餐详情和该门店可用的已有券。将固定套餐及每种合法替换配置分别表示为 offer；同一券的不同配置共用券库存 ID。
3. 记录快照和查询时间。只将当前场景可买的产品录入；未知库存、未确认的券资格不能假定可用。券叠加限制不清楚时不推断允许，以整单计价返回为准。
4. 用 `scripts/basket.py enumerate` 生成候选。金额用整数“分”。数量与多买上限写入快照。搜索达到上限时保留“不完整”标志。
5. 单点基准、估价较低的刚好买齐方案、用户允许的多买方案都应计价。对每个候选单独调用 `calculate-price`；需要包括当前门店、方式、预约时间、完整商品与配置、券，外送还包括该地址查询门店返回的 beCode；当前 calculate-price schema 不接收 addressId，不要额外传入。地址在本地快照中绑定。具体参数按实时 schema 构造。优先核价单点基准，默认每次最多核价 20 个候选；尚未核价的候选如实披露。不要按商品小计提前排除可能达到配送减免门槛的方案。
6. 可使用 `scripts/quote_live.py snapshot.json search.json --out private/live-quotes` 自动构造官方计价参数并通过 `mcd_adapter.py` 核对主商品编号、数量和费用总额；套餐子项按原始请求和详情绑定，官方报价不逐项回显。将官方成功响应映射为 quotes 文件；整单失败或资格不符标记为 rejected；网络失败不算有效报价。报价取最终应付总额，不能再加一次已包含的费用。留存本地原始请求/响应索引，导入记录并不等于程序自动验证官方签名。
7. 用 `scripts/basket.py rank` 排序。快照有效窗口 15 分钟、报价窗口 5 分钟是项目自身的保守限制，官方可能更早变价。过期则重新查询；确定买之前再次核价。

## 输出

首先推荐“刚好买齐”中已核价最便宜的一项，给出购买清单、总价、配送/包装费、使用的券。再提供一至两项替代买法。有多买方案时单独列出多了什么、相对刚好买齐实际省多少；贵的多买方案不作为省钱推荐。

只有单点基准也经过同场景计价，才展示节省金额。明确门店、用餐方式、查询时间、核价数量和比较范围。默认说“已比较且核价成功的方案中最便宜”，不宣称全平台或全店绝对最低价。演示必须写“模拟演示，非实际价格”。

没有 Token/连接时可运行仓库的模拟演示，明确尚未真实接入。不要伪造价格、券资格、成功调用记录或 WorkBuddy 开发记录。不要让用户把 Token 发到聊天；只通过本机环境变量或隐藏输入使用。

## 执行边界

仅查询和计算；不调用创建订单、领券、积分兑换、抽奖、购买会员卡或支付工具。默认按一笔订单核价，跨店、拆单和新购付费权益不在本版范围内。Token 仅发往官方 `https://mcp.mcd.cn`，不要把请求头、地址、手机号或券码写进公开仓库。
